# Feature 需求同步與生命週期

## 需求品質與實作狀態

- `specs/current/` 是已驗收且仍有效需求的權威來源；根層 feature 是進行中或待驗收的交付工作；`specs/archive/` 保存已完成的歷史交付紀錄。
- `specs/current/` 是產品的最終現況說明。讀者只需知道「現在系統應如何運作」，不需要知道需求何時、為何或經過哪些改動才成為現況。
- 修改 current 時直接改寫相關條文，使文件只剩一份無時間脈絡的現行規則；禁止追加差異、遷移、變更紀錄、來源 feature、舊版行為、已取代決策、討論結論或驗收過程。若需要保存這些脈絡，寫入 feature/archive 或其他明確的歷史文件，不放 current。
- Current 條文不得使用「原本／以前／曾經／改為／現在改成／不再／已移除／取代」等比較或沿革措辭，也不得記錄日期、版本、commit、feature 編號或歷史連結。可用「不支援 X」描述目前產品邊界，但必須是使用者理解現況所需的明確限制，而非暗示過去曾支援。
- 需求或實作變更時，先判斷最終現況，再用終態句子覆寫 current：例如將「原本使用 A，後來改成 B」改成「系統使用 B」。若無法寫成不依賴歷史背景仍可獨立理解的現況規則，就不要寫入 current。
- 禁止為每次 feature 變更在 current 新增一段或一節。相同主題只維護一份最終規則；合併重複條文並移除不再成立的舊敘述。
- 日常需求判讀先讀 `specs/current/README.md` 及相關契約，再讀根層相關 feature。不得讀取 archive，除非使用者要求追查歷史，並標明其歷史性質。
- Specify/Clarify 維護 `checklists/requirements.md` 作為需求品質檢查。Checklist 勾選只代表需求品質檢視，不代表程式實作或交付完成。
- Plan、Tasks 產生後執行 Analyze 檢查跨文件一致性；Implement 後執行 Converge，將未完成的規格要求追加為 tasks。Converge 通過只代表可交付驗收，不代表使用者已接受。

## 現行契約同步

1. 找出變更涉及的已確認需求及產品領域，更新目前 feature 的 spec、plan、tasks。
2. 將仍有效的需求與必要技術約束同步到 `specs/current/`。不可僅依程式碼或舊規格推定新需求已獲使用者接受；不確定時標示待確認。
3. Current 契約按產品領域組織，不複製 feature 清單，也不保留任何逐次變更痕跡。完成同步後，current 必須能脫離 feature/archive 獨立閱讀並完整描述現況。

## 驗收與封存

- Implement 與 Converge 完成後，回報結果並等待使用者明確驗收。沒有明確接受就留在根層並標示待驗收。
- 使用者接受後，先同步仍有效需求至 `specs/current/`，確認文件與交付一致，再將整個 feature 目錄移至 `specs/archive/`。
- 封存保留原編號與目錄名稱。新 feature 編號取根層及 archive 中最大編號加一，永不重用或重編號。
## 檢查

- 確認 current 僅包含仍有效且已驗收的需求；待確認內容不可寫成已接受要求。
- 逐段檢查 current 是否有變更日期、feature 編號／連結、版本／commit、變更原因、舊行為、差異比較、遷移或驗收敘述；有任一項即改寫成現況或移出 current。
- 搜尋「原本、以前、曾經、改為、現在改成、不再、已移除、取代」等措辭，人工確認不是沿革敘述；移除逐次追加的需求段落，將該主題收斂成唯一現行規則。
- 讀者不需查閱 feature 或 archive，就能理解每條 current 規則；否則補足現況內容，不加入歷史說明。
- 確認封存項目已同步有效需求，根層項目狀態清楚，並檢查相對連結。
- 文件變更執行 `git diff --check` 並檢閱差異。
